## 触发条件

使用此技能当：
- 想要改变现有系统/流程/规则时
- 发现"不合理"的旧做法想要废除时
- 接手遗留系统需要改造时
- 想要推翻既有决策时

---

## 核心原则

> "在不知道栅栏为何存在之前，不要拆除它。"
> — G.K. Chesterton

### 为什么重要

许多看似"不合理"的现有事物存在是因为：
- 解决了已不存在的旧问题
- 防止了未直接观察到的风险
- 平衡了多方利益相关者
- 承载了组织的历史记忆

**贸然改变的后果**: 善意改革常导致意外负面后果，因为我们未理解原始设计约束。

## 执行框架

```
┌─────────────────────────────────────────┐
│  Step 1: 暂停 (Pause)                   │
│  不要立即行动，先观察                    │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│  Step 2: 探究 (Inquire)                 │

└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│  Step 3: 评估 (Evaluate)                │

│  基于理解而非冲动做出决策                │
└─────────────────────────────────────────┘
```

## 详细执行步骤

### Step 1: 暂停 (Pause)

**触发时问自己**:
- 我为什么认为这个需要改变？
- 我的判断是否受个人偏见影响？
- 改变的压力来自哪里？（时间/他人/自己的不适）

**行动**: 设置72小时冷静期，不做任何改动。

### Step 2: 探究 (Inquire)

**探究清单**:

```markdown
## 栅栏探究清单

### 历史背景
- [ ] 这个做法/规则何时开始？
- [ ] 当时解决了什么问题？
- [ ] 谁设计的？他们的约束条件是什么？

### 利益相关者
- [ ] 谁从这个做法中受益？（即使不明显）
- [ ] 谁可能因此受损？
- [ ] 是否有我未考虑的群体？

### 隐性价值
- [ ] 这个做法是否预防了我未见过的失败？
- [ ] 是否简化了复杂决策？
- [ ] 是否承载了某种社会/文化功能？

### 依赖关系
- [ ] 其他系统/流程是否依赖这个做法？
- [ ] 改变是否会引发连锁反应？
```

**探究方法**:
1. **询问老人**: 找参与设计的人访谈
2. **查看历史**: git log、会议纪要、文档
3. **观察数据**: 这个做法产生了什么结果（好坏）？
4. **思考极端**: 如果没有这个做法，最坏情况是什么？

### Step 3: 评估 (Evaluate)

**评估矩阵**:

| 评估维度 | 问题 | 评分(1-5) |
|----------|------|-----------|
| 原始问题仍存在？ | 当初要解决的问题现在还存在吗？ | |
| 解决方案仍有效？ | 这个做法现在还能解决问题吗？ | |
| 副作用可接受？ | 带来的负面效果是否可以接受？ | |
| 机会成本？ | 维持现状的成本vs改变的成本？ | |
| 更好的替代？ | 是否有明显更好的替代方案？ | |

**决策规则**:
- 总分 ≥ 20: 维持现状
- 总分 ≤ 10: 可以废除/改变
- 中间区域: 需要小步实验验证

### Step 4: 决策 (Decide)

**三种决策类型**:

1. **完全保留**: 原理由仍然成立，维持现状
2. **完全废除**: 原理由已消失，无负面影响
3. **条件改变**: 部分保留，部分改进（需实验验证）

## 应用场景

### 场景1: 代码重构

```
发现：项目中有一个看似多余的中间层抽象

应用Chesterton's Fence:
1. Pause: 不立即删除
2. Inquire: 查看git log → 两年前为解决数据库切换而添加
3. Evaluate: 现在只用一种数据库，但未来可能迁移
4. Decide: 保留但标记为deprecated，添加注释说明历史
```

### 场景2: 产品功能

```
发现：用户很少使用的一个复杂功能

应用Chesterton's Fence:
1. Pause: 不立即下线
2. Inquire: 查看用户反馈 → 少数大客户强烈依赖
3. Evaluate: 对90%用户无用，但对10%用户是核心
4. Decide: 不向新用户展示，但保留给现有用户
```

### 场景3: 交易策略

```
发现：旧策略中有一个限制条件似乎过于保守

应用Chesterton's Fence:
1. Pause: 不立即放宽
2. Inquire: 查看历史回撤 → 该限制在2020年3月防止了爆仓
3. Evaluate: 极端市场虽不常见，但后果严重
4. Decide: 保留限制，但添加动态调整机制
```

## 常见陷阱

### ❌ "效率陷阱"
**表现**: "这个步骤太慢了，删掉它"
**后果**: 遗漏了风险控制步骤

### ❌ "聪明陷阱"
**表现**: "这代码太蠢了，我写的更好"
**后果**: 未考虑边缘情况和兼容性

### ❌ "新鲜陷阱"
**表现**: "这是旧技术，要用最新的"
**后果**: 新技术不成熟，引入新风险

### ❌ "权威陷阱"
**表现**: "专家说应该这样做"
**后果**: 未考虑自身场景的特殊性

## 相关概念对比

| 原则 | 侧重点 | 使用时机 |
|------|--------|----------|
| **Chesterton's Fence** | 理解旧事物 | 想要改变现有做法时 |
| **第一性原理** | 拆解到本质 | 创新/设计新事物时 |
| **二阶思维** | 考虑连锁反应 | 评估决策后果时 |
| **逆向思维** | 从失败倒推 | 避免错误时 |

**组合使用**:
- 用 **Chesterton's Fence** 理解现状
- 用 **第一性原理** 探索新可能
- 用 **二阶思维** 评估改变的影响
- 用 **逆向思维** 确保不会更糟

## 执行检查清单

改变任何事物前：

- [ ] 我是否暂停并深入理解了现状？
- [ ] 我是否找到了当初设计这个做法的人并询问？
- [ ] 我是否列出了所有可能的利益相关者？
- [ ] 我是否考虑了最坏情况？
- [ ] 我是否设计了小步实验来验证改变？
- [ ] 我是否准备了回滚方案？

## 一句话总结
